¿Para qué es SyncPass?

Las fundaciones e instituciones que hacen proyectos de vinculación comunitaria (talleres, operativos, actividades en juntas de vecinos) registran hoy la asistencia en planillas de papel, aplican encuestas por correo días después y transcriben todo a mano para los informes. SyncPass digitaliza ese flujo con una app Android pensada para trabajar en terreno y sin señal.

📷 Acreditación por QR

El voluntario escanea la credencial SYNCPASS:P-0007 del asistente: de ~45 s a menos de 5 s por persona.

📶 Offline-first

Todo se guarda primero en el teléfono (Room) y se sincroniza por lotes al volver la señal, sin duplicar registros.

⭐ Encuesta inmediata

Satisfacción y utilidad (1 a 5) al terminar el evento, para subir la tasa de respuesta del 15 % a más del 65 %.

📊 Métricas y reportes

Quórum en vivo, promedios y exportación CSV para el informe de cierre, sin digitar planillas.

Perfiles de usuario

RolQué hace en SyncPass
COORDINADORDocente o coordinador(a) de proyecto. Revisa proyectos y eventos, controla el quórum y obtiene métricas, resúmenes y el CSV de asistencias.
VOLUNTARIOEstudiante monitor. Escanea QR en la entrada, inscribe en sitio a quien llega sin inscripción y aplica la encuesta.
ADMINISTRADORGestiona las cuentas de usuario (alta, consulta, activar/desactivar). Rol propio de este backend.
BENEFICIARIOAsistente comunitario. No inicia sesión en el MVP; se identifica con su QR.

¿Qué papel cumple este repositorio?

La app Android (projects-duoc\Movile\android) ya existe y funciona contra un backend de referencia local con H2 y tokens propios. Este monolito es la versión desplegable: implementa el mismo contrato de API (Movile/docs/contrato-api.md) pero con identidad gestionada por Cognito, PostgreSQL en Supabase, migraciones Flyway y despliegue en EC2 con HTTPS.

Arquitectura

📱 App Android

Kotlin · Compose · Room · WorkManager · Retrofit. Guarda localmente y sincroniza por lotes.

HTTPS · Authorization: Bearer <access token>

🌐 nginx en EC2

Termina TLS (Let's Encrypt) y reenvía a la API en 127.0.0.1:8080.

proxy local

☕ SyncPass API

Spring Boot 4 · Spring Security valida el JWT de Cognito · lógica de catálogo, sincronización, métricas y reportes.

SDK AWS (rol IAM) · JDBC (TLS)

🔐 Amazon Cognito

Usuarios, contraseñas y grupos (= roles). Emite los access tokens.

🐘 Supabase PostgreSQL

Perfiles, proyectos, eventos, participantes, asistencias y encuestas. Esquema por Flyway.

🗝️ Parameter Store

Secretos (BD y Cognito) leídos al arrancar; nunca en Git ni en disco.

Decisiones tomadas

DecisiónMotivo
El monolito implementa el contrato de la app Android (/api/auth/login, /api/sync/*, errores {"error": "..."}).La app solo tiene que cambiar la URL base; no se reescribe la capa de red. Elegido el 22-10-2026.
Se migra el dominio completo desde Movile/backend (proyectos, eventos, participantes, inscripciones, asistencias, encuestas, métricas, reportes).Sin dominio, el backend en EC2 no le serviría a la app más allá del login. Elegido el 22-10-2026.
Las contraseñas y la identidad viven en Cognito; PostgreSQL solo guarda el perfil, enlazado por el sub.La API nunca almacena contraseñas. Viene del diseño original del monolito.
Esquema con Flyway y ddl-auto=validate.Cambios de base revisables y reproducibles; Hibernate no modifica tablas.
Login por username (con email como alias) y el rol = grupo de Cognito de mayor privilegio.La app envía username; Cognito es la fuente de verdad del rol y la base se sincroniza en cada login.
El token que recibe la app es el access token de Cognito, con duración de 12 h.La app no implementa refresh; 12 h equivale a las sesiones del backend de referencia y evita reingresos en terreno.
Región us-east-1 (N. Virginia) para Cognito, EC2 y Parameter Store; Supabase sigue en Ohio.La cuenta es AWS Academy Learner Lab, que solo permite us-east-1 y us-west-2. Virginia–Ohio agrega pocos milisegundos.

  4. 22-10-2026 · Etapas 2 a 5

    • Seguridad por rol: /api/usuarios/** solo ADMINISTRADOR; métricas y reportes COORDINADOR o ADMINISTRADOR; resto autenticado.

  7. 23-10-2026 · Revisión

    Revisión de errores y prueba contra PostgreSQL real

    • PostgreSQL 17 en Docker (como Supabase): Flyway aplica V1 y V2, ddl-auto=validate pasa y la siembra funciona. Las pruebas también se corrieron sobre PostgreSQL, no solo H2.
    • Login bloqueado al recrear un usuario en Cognito: con el mismo username pero otro sub (por ejemplo, al volver a crear el User Pool) el login respondía 409 para siempre. Ahora se vuelve a vincular el perfil local y se conservan su id y su estado activo.
    • Configuración de Cognito incompleta: sin COGNITO_CLIENT_ID/COGNITO_USER_POOL_ID, o con un COGNITO_ISSUER de otro pool, la API arrancaba igual y rechazaba todo token como "expirado". Ahora no arranca y el log dice qué falta.
    • Subida de asistencias: distanciaMetros infinita (1e400) se aceptaba; ahora se rechaza ese registro con su motivo.
    • CSV: los números ya no salen en notación científica (1.0E-4 → 0.00010).
    • Se quitó hibernate.dialect de application.properties: Hibernate lo detecta solo y el aviso HHH90000025 desaparece (0 avisos al arrancar).
    • Pruebas: 2 nuevas que reproducen los errores → 33 OK, 0 fallos en H2 y en PostgreSQL 17.
